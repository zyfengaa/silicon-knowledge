# 08 — AI 芯片 TCO：从 die 到 token

> 一颗 AI 加速卡的 TCO，不是“芯片售价”除以使用年限，而是把 die、封装与 HBM、测试与良率损失、功耗与散热、失效与运维逐层相加，再除以真正卖出算力的 GPU-hour 和 token；芯片侧模型只负责把 BOM 算准，集群侧的电费、PUE、调度与故障重跑必须交给 why-ai-cluster。

---

## 为什么讲这个

前七篇回答的是“会不会坏、坏在哪、每颗多少钱”。但工程决策最终问的是另一个问题：**这套硬件每跑一小时、每生成一个 token，到底要摊多少钱？** 同一个 die，做成低良率的大芯片还是高良率的芯粒，做成高功耗高性能的板卡还是低功耗低性能的板卡，放在 80% 利用率还是 40% 利用率的集群里，$/token 可以差出数倍。

TCO 也是跨层对话的语言。芯片团队关心 BOM 与良率，系统团队关心电费、PUE 与利用率，业务团队关心 token 价格；如果三方各说各的，就容易把“芯片便宜”误当成“推理便宜”，或者把“GPU 利用率 100%”误当成“成本最优”。本篇把这条账从 die 一直算到 token，并明确哪些参数属于芯片侧、哪些属于集群侧。

**口径声明**：本篇所有价格、功耗、利用率与吞吐数字均为**示例假设或公开估算，不构成采购、报价或验收依据**。真实决策必须使用合约价、现场电价比率、实测吞吐与厂商可靠性数据。

## 核心概念

### 1. 边界：芯片/板卡 TCO 与集群 TCO

TCO 必须先问“算到哪一层”。同一颗 GPU，在不同层级下的成本可以相差一个数量级：

| 层级 | 包含内容 | 本文档的处理 |
|------|----------|--------------|
| die | 晶圆、良率、NRE 摊销 | 14-05/14-06 计算 |
| 封装 | 逻辑 die、HBM、中介层、基板、组装、测试 | 14-07 计算，本篇汇总为封装 BOM |
| 板卡 | PCB、VRM、冷板、retimer、板级连接器 | 本篇给出示例分摊 |
| 节点/机柜 | CPU、DRAM、NIC、交换机、线缆、机箱、PSU | 本篇只做每 GPU 的分摊估算 |
| 集群 | PUE、电价合约、调度利用率、故障重跑、机房租金 | **why-ai-cluster 的范围** |

本模块只对**芯片/封装/板卡 BOM**负责；下面的节点/机柜分摊与电费只是把 BOM 接到 $/GPU-hour 的示例桥接。机柜级液冷、PUE 合约、电价、调度策略、故障重跑与 checkpoint 成本不在本模块展开；本篇的 $/GPU-hour 是把集群参数当作**外生输入**的一阶估算，用于说明数量级，不替代 why-ai-cluster 的集群 TCO 分析。

### 2. TCO 的五个成本项

| 成本项 | 主要组成 | 关键驱动 | 对应笔记 |
|--------|----------|----------|----------|
| die 成本 | 晶圆、毛 die 数、良率、NRE 摊销 | 面积、D0、晶圆价格、产量 | 14-05、14-06 |
| 封装/HBM | HBM 堆栈、中介层、基板、凸点、组装 | HBM 容量与世代、中介层面积、封装良率 | 14-07、13-07 |
| 测试/良率损失 | 晶圆探针、老化、终测、SLT、KGD | 测试时间、并行 site、覆盖率、逃逸成本 | 14-07 |
| 功耗/散热 | 板卡功耗、PUE、冷却设备、机房电力 | TDP、利用率、电价、PUE | 11-03、why-ai-cluster |
| 失效/运维 | 现场失效率、备件、维修、停机、重跑 | FIT/MTBF、MTTR、checkpoint 策略 | 14-01~04、why-ai-cluster |

前两项是“买的时候付”，后三项是“用的时候付”。AI 芯片的 TCO 之所以难算，是因为后三项会随利用率和负载显著变化，而它们又反过来影响前两项的设计选择（例如为降低功耗而牺牲峰值性能）。

### 3. 从 BOM 到 $/GPU-hour

把每 GPU 的 capex 记为 `C_capex`，寿命 `L` 年，年固定运维 `C_fixed`，年电费 `C_energy`，则：

```
C_capex = Σ C_die + C_package + C_board + C_node_share + C_network + C_storage + C_install

C_hourly = [C_capex + L × (C_fixed + C_energy)] / (L × 8760 × U)
```

其中 `U` 是**有效利用率**（GPU 真正在做有用计算的时间比例），不是 `nvidia-smi` 的 GPU-Util。电费按“忙时摊、闲时也耗电”计算：

```
C_energy,yr = P_IT × PUE × 8760 × [i + (1 − i) × U] × p_e
```

- `P_IT`：每 GPU 分摊的 IT 功率（GPU + CPU/NIC/DRAM/PSU 分摊），kW；
- `PUE`：数据中心总功率 / IT 功率；
- `i`：空闲功率占满载功率的比例（示例取 0.3）；
- `p_e`：电价，美元/kWh。

代入后，**每 busy GPU-hour 的电费**为：

```
C_energy_per_busy_h = P_IT × PUE × [i + (1 − i)U] / U × p_e
```

这个式子的直觉是：capex 按“日历时间 × 利用率”摊，利用率越低，每 busy hour 越贵；电费则有一部分是“闲着也要付”的底噪。

#### Worked example（示例假设，不构成采购/报价依据）

| 项目 | 金额（美元/GPU） | 说明 |
|------|------------------|------|
| 封装后芯片 BOM | 6,020 | 沿用 14-07 示例：2×800 mm² 逻辑 die + 8×24 GB HBM |
| 板卡集成 | 1,500 | PCB、VRM、冷板、retimer、连接器 |
| 节点共享 | 8,000 | CPU、DRAM、NIC、机箱、PSU、BMC 按 8 GPU 分摊 |
| 交换/光模块/线缆 | 5,000 | 集群网络按 GPU 分摊 |
| 存储与管理 | 2,000 | 并行文件系统、管理节点、监控 |
| 安装调试 | 1,000 | 上架、布线、验收 |
| **Capex 合计** | **23,520** | — |

运行假设：`L = 5` 年、`U = 0.8`、`P_IT = 1.2 kW`、`PUE = 1.25`、`i = 0.3`、`p_e = $0.08/kWh`、维护 3% capex/年、失效与维修 1.5% capex/年、场地/网络运维 $210/年。

```
年电费 = 1.2 × 1.25 × 8760 × (0.3 + 0.7 × 0.8) × 0.08 ≈ $904
年固定 = 23,520 × (3% + 1.5%) + 210 ≈ $1,268
5 年 TCO = 23,520 + 5 × (904 + 1,268) ≈ $34,382
busy hours = 5 × 8760 × 0.8 = 35,040
$/GPU-hour ≈ 34,382 / 35,040 ≈ $0.98
```

注意：`$0.98/GPU-hour` 是**自有硬件的摊销成本**，不是云厂商报价；云价还包含毛利、利用率风险、网络与支持服务。它与 11-08 习题里 `$2/H100 GPU-h` 的租用价属于不同口径，不能直接比较。

### 4. 从 $/GPU-hour 到 $/token

**训练**的 token 成本由模型 FLOPs（约 `6N`，N 为参数量）、峰值算力、MFU 与 GPU 小时决定：

```
tokens_per_GPU_hour = 3600 × MFU × P_peak / (6N)

$/token = C_hourly / tokens_per_GPU_hour
```

以 70B 模型、H100 SXM 的 989 TFLOPS BF16 dense（`SPECS.md` §1）、MFU = 40% 为例：

```
tokens_per_GPU_hour = 3600 × 0.40 × 989e12 / (6 × 70e9) ≈ 3.39e6
$/M token = 0.98 / 3.39 ≈ $0.29
```

训练 15T token 需要约 `15e12 / 3.39e6 ≈ 4.42e6` GPU-hours；按 1,000 卡则约 4,424 小时（184 天），成本约 434 万美元。这是“自有硬件摊销”口径，不含失败重跑、数据管道与人力。

**推理**的 token 成本由单卡吞吐决定：

```
$/token = C_hourly / (3600 × R_tok)
```

`R_tok` 是每 GPU 每秒生成的 token 数（output token）。它强烈依赖模型大小、batch、序列长度、量化精度与 SLO：

| 场景 | 每 GPU 吞吐（token/s） | 每 GPU-hour token | $/M token（C=$0.98/h） |
|------|------------------------|-------------------|-------------------------|
| 70B 训练（40% MFU） | ~942 | 3.39M | ~$0.29 |
| 大 batch 推理 | 1,000 | 3.60M | ~$0.27 |
| 常规在线服务 | 250 | 0.90M | ~$1.09 |
| 低利用率/低 batch 服务 | 60 | 0.22M | ~$4.54 |

**$/token 不是单一数字**：训练 token 与推理 token 的成本结构不同；推理还要区分 prefill（compute-bound）与 decode（memory-bound）、输入 token 与输出 token、TTFT/TPOT SLO。任何跨厂商、跨模型的 $/token 比较，必须先对齐精度、batch、序列长度与 SLO。

最重要的结论不是某个具体百分比，而是**利用率与 BOM 结构共同决定 TCO**：在 HBM 密集型产品里，存储与封装可能比逻辑 die 更主导 BOM；在长寿命、低利用率的部署里，capex 分摊可能比电费更主导。下一节的敏感性表给出具体数字。

## 深入理解

### 1. 与 13-05/06/07 的接口：工艺与封装决定 BOM 的上游

[13-05 工艺节点](../../13-工艺制造与先进封装/notes/05-process-nodes.md) 决定晶圆价格与每平方毫米的晶体管数。节点命名不是物理尺寸，不能拿“5nm 比 7nm 便宜/贵”直接比较；真正进入成本模型的是**每片晶圆价格、良率与可用面积**。

[13-06 Chiplet 与 UCIe](../../13-工艺制造与先进封装/notes/06-chiplet-ucie.md) 决定“拆 die”的收益与代价：拆开能提高良率，但增加 die-to-die 互连、封装面积、KGD 测试与组装步骤。14-06 的面积弹性 `1 + A·D0` 是收益侧，13-07 的封装成本是代价侧。

[13-07 先进封装](../../13-工艺制造与先进封装/notes/07-advanced-packaging.md) 决定中介层面积、HBM 堆叠、凸点间距与封装良率。CoWoS 的中介层按 reticle 倍数计价，面积越大，每片可排数越少、缺陷概率越高；这部分成本在 14-07 汇总进封装 BOM，再在本篇进入 capex。

### 2. 与 [14-05](05-yield-models.md)/[14-06](06-die-cost.md)/[14-07](07-packaging-test-cost.md) 的接口：一条从良率到 BOM 的链

```
14-05 良率 Y(A, D0, α)
   ↓
14-06 每颗合格 die 成本 = 晶圆价格 / (毛 die 数 × Y) + 测试 + NRE/Q
   ↓
14-07 封装 BOM = (Σ die + 材料 + 组装 + 测试) / Y_package + NRE_pkg/Q
   ↓
14-08 capex → $/GPU-hour → $/token
```

每一层都会放大上游的波动：D0 翻倍让 die 成本约翻倍，但到了封装 BOM 只增加约 30%，到了 $/GPU-hour 只增加约 10%；反过来，HBM 价格或封装良率的变化会直接击中 BOM 的大头。**成本模型的价值不在于精确到个位数，而在于识别哪一层是主导项。**

### 3. 与 11-03/11-08 的接口：功耗、MFU 与利用率

[11-03 功耗与散热](../../11-系统分析与性能工程/notes/03-power-thermal.md) 提供 TDP、结温、热阻与 DVFS 的语言。TCO 里的 `P_IT` 不是 GPU TDP，而是整板/整节点的 IT 功率分摊；`PUE` 则把 IT 功率换算成设施功率。按 `SPECS.md` §1，H100 SXM 为 700 W、B200 为 1,000 W、B300/GB300 为 1,400 W；单卡 TDP 不能直接乘以电价，必须加上 CPU、DRAM、NIC、PSU 损耗与冷却。

[11-08 端到端案例](../../11-系统分析与性能工程/notes/08-end-to-end-case.md) 提供 MFU、GPU-hours 与训练成本的算法。本篇的 $/token 公式与 11-08 的 `6N`、`MFU`、`GPU-hours` 是同一套账，只是本篇把 `$/GPU-hour` 换成了自有硬件的摊销成本，而 11-08 用的是租用价。

### 4. 失效与运维如何进入 TCO

可靠性不是“坏了再修”的杂项，而是 TCO 的固定项：

- **现场失效率**：用 FIT/MTBF 估算每年失效台数；`1 FIT = 1 次失效 / 10^9 器件小时`，整卡 FIT 要把 GPU、HBM、板卡与连接器相加；
- **维修、停机与运维**：备件、人工、物流与返修；训练中断后从 checkpoint 重跑，损失的是 GPU-hours；大规模集群的监控、告警与慢节点排查也是持续成本。

这些项的细节属于 why-ai-cluster 的运维与调度范围；本模块只提供芯片侧的失效率输入（14-01~04）与封装/测试侧的逃逸风险（14-07）。一个常见的错误是只算硬件更换费、不算停机与重跑，导致 TCO 被低估。

### 5. 什么时候不该用这套模型

架构探索早期、采购报价、跨代比较与跨模型 $/token 比较都不适合直接套用单点 TCO：输入全是假设，或口径未对齐；此时应使用区间、敏感性与同口径实测，而不是一个看起来精确的数字。

---

## 总结

AI 芯片 TCO 是五层成本的叠加：die、封装/HBM、测试/良率、功耗/散热、失效/运维；每层都有自己的物理与统计规律。把 capex 按“寿命 × 利用率”摊、把电费按“忙时 + 闲时底噪”摊，才能得到有意义的 $/GPU-hour；再用 `6N`、MFU 与吞吐把它换算成 $/token。芯片侧模型负责把 BOM 算准，集群侧的电费、PUE、调度与故障重跑必须交给 why-ai-cluster。所有数字都是示例假设或公开估算，不构成采购、报价或验收依据；真正可用的结论来自“参数区间 + 敏感性分析”，而不是一个看起来精确的单点。
